Constant folding and simplification

LLVM.constant_fold_cast — Function
constant_fold_cast(opcode, c::Constant, T::LLVMType, dl::DataLayout)

Fold the cast opcode (e.g., LLVM.Opcode.Trunc) of the constant c to type T, using LLVM's constant folder and the data layout dl. Returns the resulting constant, which can be a constant expression, or nothing if the cast cannot be folded (e.g., since LLVM 18, for some casts that would need to be constant expressions, which LLVM no longer supports). source
LLVM.simplify_instruction — Function
simplify_instruction(inst::Instruction)

Simplify an instruction, like the instsimplify pass: returns a simpler value that the instruction is equivalent to (e.g., an operand, or a constant), or nothing if there is none, e.g., add i32 %x, 0 simplifies to %x, and and i1 %c, false to false. This does not change the IR: to fold the instruction, replace its uses by the returned value (replace_uses!), and erase it. The instruction must be part of a function in a module, whose data layout is used.

This uses LLVM's simplifyInstruction, which also implements the InstSimplifyFolder that C++ code can use to simplify instructions as an IRBuilder creates them.

Constant ranges and known bits

LLVM.ConstantRange — Type
ConstantRange

A range of integers of a certain bit width, like LLVM's ConstantRange: the values from lower (inclusive) up to upper (exclusive), wrapping around at the end of the integer domain if upper is smaller than lower (a wrapped range). Equal bounds denote the empty range when they are zero, and the full range when they are the maximum value.

ConstantRange(nbits, lower, upper)
ConstantRange(nbits, value)
ConstantRange(nbits; empty=false)

Create the range of nbits-bit integers from lower up to upper, containing only value, or containing all (or, with empty=true, none) of the nbits-bit integers. Negative bounds and values are interpreted as two's complement integers.

Constant ranges are immutable values, and LLVM's own implementation of ranges is used to compute with them, e.g., using +, -, *, << or binary_op. Ranges are over-approximations: an operation can return a range that contains more values than the exact result (e.g., intersect_with returns a range containing the intersection of two ranges, as the exact intersection may not be a single range). Operations on ranges of different bit widths are not supported.

Properties

The bounds and extrema of a range are integers of a type that depends on the bit width: UInt64 or Int64 for up to 64 bits, UInt128 or Int128 for up to 128 bits, and BigInt for wider ranges.

  • r.nbits: the bit width of the integers in the range.
  • r.lower, r.upper: the bounds of the range, as unsigned integers.
  • r.unsigned_min, r.unsigned_max: the smallest and largest value in the range when interpreted as unsigned integers.
  • r.signed_min, r.signed_max: the smallest and largest value in the range when interpreted as signed integers.
  • r.all_nonnegative: whether all values in the range are non-negative when interpreted as signed integers (which is the case for the empty range).

The extrema are not defined for the empty range.

Use x in r to check whether the integer x is in the range (where negative integers are interpreted as two's complement integers, and integers that don't fit in the bit width are never in the range), and issubset(a, b) to check whether all values in range a are in range b. Ranges can also be read from, and converted to !range metadata, using ConstantRange(md::MDNode) and MDNode(r).

See also: isfullset, iswrappedset

LLVM.binary_op — Function
binary_op(opcode, a::ConstantRange, b::ConstantRange; nuw=false, nsw=false)

Compute the range of the result of the binary operator opcode (e.g., LLVM.Opcode.Add) applied to values in the ranges a and b. With nuw or nsw, only the results of operations that do not wrap in the unsigned or signed sense are included, as for instructions with those flags (which produce poison otherwise). This does not prove that an operation does not wrap. Operations for which LLVM does not know how to use these flags ignore them, which is less precise, but still correct (on LLVM before 19, this is the case for multiplications, and before 20 for left shifts).

The common operators are also available using Julia's operators: a + b, a - b, a * b, a & b, a | b, xor(a, b), a << b, a >> b (arithmetic shift), and a >>> b (logical shift).

Assumptions and value tracking

LLVM.AssumptionCache — Type
AssumptionCache

The llvm.assume calls of a function, as cached by LLVM's assumption cache. It is obtained from the analysis manager of a custom pass (am[AssumptionCache]), and used by other analyses to find the assumptions that are relevant to a value.

  • iterating the cache yields the assumptions (as CallInsts) of the function;
  • ac[v] returns the assumptions that affect the value v, as a vector of AssumptionEntry;
  • push!(ac, assume) registers an llvm.assume call that the pass created, which is required for other analyses to see it;
  • empty!(ac) clears the cache, so that it is rebuilt from the function when it is used next.

Unlike other analyses, the assumption cache is not invalidated when a pass changes the function: passes that create assumptions must register them, while deleted assumptions are handled automatically. The assumptions that are returned are a snapshot.

source
LLVM.AssumptionEntry — Type
AssumptionEntry

An assumption that affects a value, as returned by indexing an AssumptionCache:

  • entry.assume: the llvm.assume call;
  • entry.bundle_index: the (1-based) index of the operand bundle of the assumption that affects the value, or nothing if the value is affected by the condition of the assumption.
source
LLVM.ConstantRange — Method
ConstantRange(v::Value; signed=false, at=nothing, assumptions=nothing, domtree=nothing,
              datalayout=nothing, use_instruction_info=true)

Compute a range of the values of the integer (or vector of integers) v, using LLVM's value tracking (computeConstantRange). It analyzes the instructions computing v, and optionally the assumptions that hold at instruction at (which needs the AssumptionCache and, for assumptions that are not in the same block, the DomTree). With signed=true, a range that does not wrap in the signed domain is preferred. The data layout defaults to that of the module containing at or v; with use_instruction_info=false, metadata and flags of instructions (like !range or nuw) are ignored.

The result is a fact about v if it is not poison: it does not prove that v is not poison (see is_guaranteed_not_to_be_poison).

The keyword arguments are the same as for ConstantRange(::Value). A data layout is required, so if neither at nor v are part of a module, it needs to be passed explicitly.

The keyword arguments are the same as for ConstantRange(::Value).

Lazy value info

LLVM.LazyValueInfo — Type
LazyValueInfo

LLVM's lazy value information analysis, which computes the ranges of integer values at specific points of a function, taking into account the conditions of the branches that lead there (and assumptions). It is obtained from the analysis manager of a custom pass (am[LazyValueInfo]), and queried by constructing a range:

ConstantRange(lvi, v; at::Instruction, undef_allowed=false)
ConstantRange(lvi, v; from::BasicBlock, to::BasicBlock, at=nothing)
ConstantRange(lvi, use::Use; undef_allowed=false)

These compute the range of the integer (or vector of integers) v at instruction at, on the edge between blocks from and to (optionally at an instruction at in to), or at a use of v (LLVM 16+), which also takes into account the instruction using it. With undef_allowed=true, the range may not include all values of a v that is undef.

The analysis caches its results, which become stale when the function changes (see invalidate!).

Loops and scalar evolution

LLVM.LoopInfo — Type
LoopInfo

The natural loops of a function, as computed by LLVM's loop analysis. It is obtained from the analysis manager of a custom pass (am[LoopInfo]). Indexing it with a basic block, li[bb], returns the innermost Loop containing the block, or nothing if the block is not part of a loop. Iterating it yields the outermost loops of the function.

source
LLVM.Loop — Type
Loop

A natural loop, as identified by LoopInfo. Loops are owned by the loop analysis. Use bb in loop or inst in loop to check whether a basic block or instruction is part of the loop (or of one of its nested loops), and is_loop_invariant to check whether a value is defined outside of it.

Like the loop analysis itself, loops must not be used after the pass that obtained them returns, or after the analysis was invalidated.

Properties

  • loop.header: the header block of the loop, which dominates all of its blocks.
  • loop.parent: the loop containing this loop, or nothing for an outermost loop.
  • loop.depth: the nesting depth of the loop (1 for an outermost loop).
  • loop.blocks: the blocks of the loop, including those of nested loops, starting with the header (a read-only vector).
  • loop.subloops: the loops that are directly nested in this loop (a read-only vector).
  • loop.exit_blocks: the blocks outside of the loop that it branches to, without duplicates (an iterable that finds them when it is iterated).
  • loop.latch: the block that branches back to the header, or nothing if there are several.
  • loop.preheader: the only predecessor of the header that is outside of the loop, if it only branches to the header, or nothing otherwise (e.g., because the loop is not in the simplified form that the loop-simplify pass creates).
source
LLVM.ScalarEvolution — Type
ScalarEvolution

LLVM's scalar evolution analysis, which represents integer and pointer values as symbolic expressions (SCEVs), e.g., to recognize induction variables of loops. It is obtained from the analysis manager of a custom pass (am[ScalarEvolution]).

  • se[v]: the expression for the integer or pointer value v (see is_scevable);
  • scev_add, scev_minus, scev_mul, scev_cast: build new expressions;
  • ConstantRange(se, s; signed=false): the range of the values of an expression;
  • is_loop_invariant, backedge_taken_count, step_recurrence: loop-related queries.

Expressions are owned by the analysis and uniqued, so that expressions that are equal are also identical (==). The analysis caches its results, which become stale when the function changes.

source
LLVM.SCEV — Type
SCEV

A symbolic expression for a value, as computed by ScalarEvolution. Expressions are represented by a concrete subtype for each kind of expression: SCEVConstant, SCEVUnknown (a value that the analysis does not look into), SCEVAddExpr, SCEVMulExpr, SCEVUDivExpr, SCEVAddRecExpr (an add recurrence, like an induction variable of a loop), casts (SCEVTruncateExpr, SCEVZeroExtendExpr, SCEVSignExtendExpr, SCEVPtrToIntExpr), minima and maxima (SCEVUMaxExpr, SCEVSMaxExpr, SCEVUMinExpr, SCEVSMinExpr, SCEVSequentialUMinExpr), SCEVVScale (LLVM 17+), and SCEVCouldNotCompute (e.g., for the difference of pointers with different bases). Like the analysis itself, expressions must not be used after the pass that obtained them returns, or after the analysis was invalidated.

Properties

  • s.type: the type of the expression (not available for SCEVCouldNotCompute).
  • s.operands: the operands of the expression (a vector of SCEVs).
  • s.value: the ConstantInt of a SCEVConstant, or the value of a SCEVUnknown.
  • s.loop: the Loop of a SCEVAddRecExpr.
  • s.start: the start value of a SCEVAddRecExpr (its first operand).
  • s.affine: whether a SCEVAddRecExpr is affine, i.e., has a step that is invariant in its loop (when it has two operands: {start,+,step}).
  • s.nuw, s.nsw, s.nw: the no-wrap flags of an n-ary expression (SCEVAddExpr, SCEVMulExpr, SCEVAddRecExpr, and the minima and maxima): whether it is known not to wrap in the unsigned or signed sense, and (for an add recurrence) whether it is known to never wrap back to its start value (no self-wrap). These are facts that scalar evolution proved or derived from the IR, which hold in the context of the expression.
source

Speculation

LLVM.is_safe_to_speculatively_execute — Function
is_safe_to_speculatively_execute(inst::Instruction; at=nothing, assumptions=nothing,
                                 domtree=nothing)

Check whether the instruction can be executed without the conditions that guard it, e.g., moved out of a loop or a conditional block: it has no side effects, and cannot trap or cause undefined behavior. The optional context instruction at (where the instruction would be executed), and the assumption cache and dominator tree that are used to reason about it, can prove more instructions safe (the assumption cache is only used since LLVM 16). This does not check that the operands of the instruction are available, and for instructions that read memory (e.g., a load that is known to be dereferenceable), that moving them does not change the value they read.

Memory SSA

LLVM.MemorySSA — Type
MemorySSA

LLVM's MemorySSA analysis, which represents the memory operations of a function and the dependences between them in SSA form: every instruction that may write memory defines a new state of memory (a MemoryDef), which depends on the previous one, every instruction that only reads memory uses a state (a MemoryUse), and a MemoryPhi merges the states that reach a block from its predecessors.

It is provided to custom loop passes in a loop-mssa(...) pipeline (ar[MemorySSA], see LoopAnalysisResults), which need to keep it up to date when they move, create or remove memory operations, using a MemorySSAUpdater. Function passes can get it from their analysis manager (am[MemorySSA], see FunctionAnalysisManager). In both cases, it is borrowed from the analysis manager, and must not be used after the pass returns.

MemorySSA depends on the dominator tree, and is invalidated with it: a function or module pass that kept MemorySSA up to date preserves it with PreservedAnalyses(MemorySSA, CFGAnalyses) if it did not change the control-flow graph, or PreservedAnalyses(MemorySSA, DomTree) if it updated the dominator tree as well. PreservedAnalyses(MemorySSA) on its own does not keep MemorySSA.

  • memory_access(mssa, inst): the access of an instruction, or the phi of a block (see memory_access);
  • memory_accesses(mssa, bb): the accesses of a block, in order;
  • live_on_entry(mssa): the definition of the state of memory on entry of the function;
  • verify(mssa): check that it is consistent with the IR. This only checks something with a build of LLVM that has assertions enabled, which aborts if it is not.
source
LLVM.MemoryAccess — Type
MemoryAccess

An access of MemorySSA: a MemoryUse or MemoryDef (both MemoryUseOrDef) of an instruction, or a MemoryPhi of a block. Accesses are owned by MemorySSA: they must not be used after it is no longer valid, or after they were removed from it (e.g., using remove_access!).

Properties

  • access.block: the block that the access is in;

  • access.instruction (for uses and definitions): the instruction that accesses memory, or nothing for the live-on-entry definition;

  • access.defining_access (for uses and definitions): the access that defines the state of memory that the instruction uses or changes (a MemoryDef or MemoryPhi), or nothing for the live-on-entry definition.

  • phi.incoming (for phis): the states of memory that reach the block of the phi, as a vector of (access, block) tuples of the incoming access and the predecessor that it comes from.

source

MemoryUseOrDef <: MemoryAccess

Passes that move, create or remove memory operations keep MemorySSA up to date using an updater:

LLVM.MemorySSAUpdater — Type
MemorySSAUpdater(mssa::MemorySSA)
MemorySSAUpdater(f, mssa::MemorySSA)

Create an updater for mssa, which keeps it valid while a pass changes the memory operations of a function, using LLVM's MemorySSAUpdater. A pass first changes the IR, e.g., moves an instruction, and then the corresponding access:

  • move_to_place!: move the access of an instruction that was moved;
  • create_access_in_block! followed by insert_def! or insert_use!: add an access for a new instruction;
  • remove_access!: remove the access of an instruction that is about to be erased.

The updater refers to mssa, so it can only be used while that is valid: a pass that is given MemorySSA creates the updater, and disposes of it before it returns (e.g., using the do-block form). It keeps state between operations, which the operations of a pass share by using the same updater, like the C++ passes do.

This object needs to be disposed of using dispose, or by using the do-block form.

LLVM.remove_access! — Function
remove_access!(updater::MemorySSAUpdater, access::MemoryUseOrDef; optimize_phis=false)
remove_access!(updater::MemorySSAUpdater, inst::Instruction; optimize_phis=false)

Remove the access of an instruction from MemorySSA, e.g., of an instruction that is about to be erased, replacing its uses by its defining access. Given an instruction without an access, this does nothing. With optimize_phis=true, phis that become trivial (i.e., merge a single state) are removed as well.

Phis cannot be removed this way: LLVM can only remove a phi that is unused or merges a single state, and otherwise leaves its users without a defining access.

LLVM.move_to_place! — Function
move_to_place!(updater::MemorySSAUpdater, access::MemoryUseOrDef, bb::BasicBlock, where::Symbol)

Update MemorySSA for an instruction that was moved to the block bb: move its access to the given place among the accesses of the block, which is :beginning, :end, or :before_terminator (which is :end, unless the terminator itself has an access, e.g., an invoke). The instruction must have been moved to that place first, e.g., to the beginning of the block (after its phis), or before its terminator. The accesses that used the moved access, and the access itself, are then updated, like when it is created there.

move_before! and move_after! move an access next to another one instead, after its instruction was moved next to the other's.

LLVM.create_access_in_block! — Function
create_access_in_block!(updater::MemorySSAUpdater, inst::Instruction, bb::BasicBlock,
                        where::Symbol; definition=nothing)
create_access_before!(updater::MemorySSAUpdater, inst::Instruction,
                      access::MemoryUseOrDef; definition=nothing)
create_access_after!(updater::MemorySSAUpdater, inst::Instruction,
                     access::MemoryAccess; definition=nothing)

Create the access of a new instruction in the block bb that it was inserted in, at a place among the accesses of the block (:beginning, :end or :before_terminator, see move_to_place!), or before or after another access in its block, and return it: a MemoryUse or MemoryDef, depending on how the instruction accesses memory. The instruction must be at the corresponding place in the block.

Returns nothing if the instruction does not read or write memory, in which case MemorySSA does not need an access for it. MemorySSA also leaves out instructions that alias analysis finds not to access memory (e.g., a call to a function that only accesses memory that is not otherwise accessible), which this only detects for a place in a block on LLVM 19 and later: creating an access for such an instruction is invalid otherwise.

The access is created with definition as its defining access (a MemoryDef or MemoryPhi), which is not checked. Unless that is known to be correct, e.g., when the instruction replaces another one in the same place, leave it out and insert the access afterwards using insert_def! or insert_use!, which find its defining access and update the accesses that depend on it.

Creating an access for an instruction that already has one leaves the existing access inaccessible, and it must be removed using remove_access!.

source
LLVM.insert_def! — Function
insert_def!(updater::MemorySSAUpdater, def::MemoryDef; rename=false)
insert_use!(updater::MemorySSAUpdater, use::MemoryUse; rename=false)

Insert a new access (created using create_access_in_block!) into MemorySSA: find its defining access, and for a definition, make the accesses that now see the state it defines use it, adding phis where needed. With rename=true, the uses of the states that the access dominates are updated as well, which is needed unless they cannot be affected, e.g., when the access was created at the end of a block with no other accesses after it. Julia's and LLVM's passes pass rename=true when they move or clone memory operations.
